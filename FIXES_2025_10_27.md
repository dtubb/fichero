## Summary

## Issue 1: Workflows Showing as "Failed" When They Succeeded

### Problem
- Workflows that completed successfully were showing ❌ Failed or ⚠️ Partial in the Inspector
- Activity Monitor showed ✓ Completed correctly
- Logs showed all steps succeeded with "failed: 0"

### Root Cause
**Manifest Parsing Bug** in `director_integration.py:1117`

The code checked for a `success` field in manifest entries:
```python
if entry.get('success'):
    step_data['successful_files'] += 1
else:
    step_data['failed_files'] += 1  # Everything marked as failed!
```

But actual manifest entries look like this (NO `success` field):
```json
{"outputs":["file.txt"],"source":"file.jpg","details":{...}}
```

Since `entry.get('success')` returned `None`, ALL entries were marked as failed.

### Fix Applied
**File:** `src/fichero/library/director_integration.py:1112-1145`

Changed the logic to recognize success via the `outputs` field:
```python
# A manifest entry is successful if:
# 1. It has explicit success=True, OR
# 2. It has outputs and no error field (implicit success)
has_error = 'error' in entry and entry['error']
has_outputs = 'outputs' in entry and entry['outputs']
explicit_success = entry.get('success', False)

if has_error:
    step_data['failed_files'] += 1
elif explicit_success or has_outputs:
    if entry.get('skipped'):
        step_data['skipped_files'] += 1
    else:
        step_data['successful_files'] += 1
else:
    step_data['failed_files'] += 1
```

## Issue 2: ProcessingResult Status Ignored Manifest Data

### Problem
Even after fixing manifest parsing, the `ProcessingResult.status` field was set using Director's `result.success` flag, which had the same manifest parsing bug.

### Root Cause
**File:** `director_integration.py:873`
```python
status='success' if result and result.success else 'failed'
```

This trusted Director's incorrect `result.success` flag instead of using the corrected manifest data.

### Fix Applied
**File:** `src/fichero/library/director_integration.py:869-893`

Changed to determine status from parsed manifest summary:
```python
# Determine overall workflow status from parsed manifests
summary = artifacts_metadata.get('summary', {})
failed_steps = summary.get('failed_steps', 0)
successful_steps = summary.get('successful_steps', 0)

if failed_steps > 0:
    workflow_status = 'partial' if successful_steps > 0 else 'failed'
elif successful_steps > 0:
    workflow_status = 'success'
else:
    # Fallback to Director's result if no steps parsed
    workflow_status = 'success' if result and result.success else 'failed'

processing_result = ProcessingResult(
    ...
    status=workflow_status,  # Now uses accurately parsed manifest data
    ...
)
```

## Issue 3: Batch Processing Instead of Folder Processing

### Problem
When in a subfolder with no files selected and clicking "Process":
- Expected: Process the folder as a single unit
- Actual: Created a batch of individual files (`batch_4_files`)
- This failed because batch processing is different from folder processing

### Root Cause
**File:** `collection_view.py:2036-2039`

When no selection was made, the code collected all visible FILE items:
```python
# Only include file items, not folder items
item_type = getattr(row, 'type', 'file')
if item_type == 'file':
    visible_items.append(item_id)
```

This created a list of individual files to process as a batch, rather than processing the folder.

### Fix Applied
**File:** `src/fichero/windows/main/views/collection/collection_view.py:2026-2108`

Added logic to detect when in a subfolder and process the folder item instead:
```python
if selected_item_id:
    # Process selected item
    item_ids = [selected_item_id]
else:
    # No selection - check if we're in a subfolder
    if self.current_path:
        # In a subfolder - process the folder itself, not individual files
        folder_item = None
        for item in all_items:
            if item.type == 'folder':
                # Build path from parent hierarchy
                path_parts = []
                current_item = item
                while current_item:
                    path_parts.insert(0, current_item.name)
                    if current_item.parent_id:
                        parent_item = next((i for i in all_items if i.id == current_item.parent_id), None)
                        current_item = parent_item
                    else:
                        break

                item_path = '/'.join(path_parts) if path_parts else ''

                if item_path == self.current_path:
                    folder_item = item
                    break

        if folder_item:
            # Process the folder as a single item
            item_ids = [folder_item.id]
        else:
            # Fallback to visible files
            ...
    else:
        # At collection root - collect visible files
        ...
```

## Issue 4: Large Images Causing Qwen API Timeouts/Crashes

### Problem
Large images being sent to Qwen API were causing:
- Timeout errors after 240 seconds
- System crashes or memory issues
- Complete workflow failures

### Root Cause
**File:** `transcribe_qwen_max.py:33-53`

The code resized images to a fixed 1024px maximum and had a 240 second timeout. If an image was too complex or large, it would:
1. Take too long to process (timeout)
2. Fail after 3 retries at the same size
3. Never try smaller sizes that might succeed

### Fix Applied
**File:** `src/fichero/tools/transcribe_qwen_max.py:30-66, 110-233`

Implemented **progressive size reduction on timeout**:

```python
# encode_image now accepts max_size parameter
def encode_image(image: Image.Image, max_size: int = 1024) -> str:
    """Encode image with configurable max size
    Progressive values: 1024 (default) -> 768 -> 512 -> 256
    """
    # ... resizing logic ...

# process_image_sync now tries progressively smaller sizes
size_attempts = [1024, 768, 512, 256]

for size_index, max_size in enumerate(size_attempts):
    base64_image = encode_image(image, max_size=max_size)

    # Try API call at this size (2 retries per size)
    try:
        completion = client.chat.completions.create(...)
        break  # Success! Stop trying smaller sizes
    except Exception as api_error:
        # Check if timeout
        is_timeout = "timeout" in str(api_error).lower()

        if is_timeout and size_index < len(size_attempts) - 1:
            # Try next smaller size
            next_size = size_attempts[size_index + 1]
            tool_logger.warning(f"⏱️ Timeout at {max_size}px, trying {next_size}px")
            break
```

**Benefits:**
- Images that timeout at 1024px can succeed at 768px, 512px, or 256px
- Automatic fallback prevents complete workflow failures
- Logs show which size succeeded for debugging
- Reduced timeout to 180s (3 minutes) since we now have size fallbacks

## Issue 5: Toga Selection Property Read-Only Error (NEW - October 29, 2025)

### Problem
When trying to process a folder with nothing selected, GUI crashed with error:
```
Failed to update items list: can't set attribute 'selection'
```

### Root Cause
**File:** `collection_view.py` (multiple locations)

In Toga 0.5.2, the `selection` property on `DetailedList` is read-only and cannot be directly assigned. The code tried to clear selection with:
```python
self.items_list.selection = None
```

This raised `AttributeError` and crashed the GUI.

### Fix Applied
**File:** `src/fichero/windows/main/views/collection/collection_view.py`

Wrapped all selection assignments in try/except blocks at 6 locations:
- Line 370 (already had exception handling, no change)
- Line 477 (toolbar back navigation)
- Lines 1354, 1367 (list update/refresh)
- Lines 1802, 1816 (folder navigation)

```python
try:
    self.items_list.selection = None
    logger.debug("🔄 Reset selection after navigation")
except AttributeError:
    logger.debug("Could not clear selection (read-only property)")
```

**Result:** GUI loads properly and selection clearing fails gracefully without crashes.

## Issue 6: Files Treated as Batch Instead of Catalogue by Parent Folder (NEW - October 29, 2025)

### Problem
When processing multiple files with no selection:
- Expected: Files in the same parent folder should process as ONE catalogue unit (files process individually but share catalogue output)
- Actual: Created `batch_X_files` which failed with "Input manifest does not exist"

**User requirement:** "Files in same folder = one catalogue"

### Root Cause
**File:** `director_integration.py:312-318`

When processing multiple files, the code only checked if there was one file. If not, it processed ALL files as a single batch regardless of their folder structure:
```python
if single_file_selection:
    # Process one file
else:
    # Multiple files - process as batch
    batch_task_ids = await self._process_file_batch(...)
```

Batch processing expects a different manifest structure than folder/catalogue processing, which is why it failed.

**The real issue:** Files weren't grouped by their parent folder. The system should recognize that files in the same folder belong to the same catalogue.

### Fix Applied
**File:** `src/fichero/library/director_integration.py:277-411`

Implemented **parent-based grouping** logic:

```python
# Group files by their parent_id
# Files with same parent_id = one catalogue
from collections import defaultdict
files_by_parent = defaultdict(list)

for item_id, item, input_path in file_items:
    parent_key = item.parent_id if item.parent_id else "_root_"
    files_by_parent[parent_key].append((item_id, item, input_path))

logger.info(f"Grouped {len(file_items)} files into {len(files_by_parent)} catalogue groups")

# Process each group as one catalogue
for parent_key, group_files in files_by_parent.items():
    if len(group_files) == 1:
        # Single file in group - process as individual file
        task_id = await self._process_single_file(...)
    else:
        # Multiple files in same parent - process as ONE catalogue
        # 1. Create temporary directory with symlinks
        temp_dir = Path(tempfile.mkdtemp(prefix=f"fichero_catalogue_{parent_key}_"))

        for _, item, input_path in group_files:
            symlink_path = temp_dir / input_path.name
            os.symlink(input_path, symlink_path)

        # 2. Process temp directory as a single folder/catalogue
        task_id_list = await self._process_single_folder(
            first_item_id, temp_dir, catalogue_output_path,
            plan_name, workflow_name, collection_id
        )
```

**File:** `src/fichero/windows/main/views/collection/collection_view.py:2115-2118`

Updated log message to indicate catalogue processing:
```python
scope_text = f"{len(item_ids)} visible files (at collection root, as catalogue)"
logger.info(f"Processing {len(item_ids)} visible files at collection root as catalogue unit")
```

### How It Works Now

**Examples:**

1. **5 files at root (no parent):**
   - Groups: `{_root_: [file1, file2, file3, file4, file5]}`
   - Result: **1 catalogue** containing all 5 files

2. **3 files at root + 1 folder:**
   - Groups: `{_root_: [file1, file2, file3]}` + folder processed separately
   - Result: **2 catalogues** (root files = 1, folder contents = 1)

3. **2 files in "Documents" folder + 3 files in "Photos" folder:**
   - Groups: `{documents_id: [file1, file2], photos_id: [file3, file4, file5]}`
   - Result: **2 catalogues** (one per folder)

4. **1 file in "Documents" + 1 file in "Photos":**
   - Groups: `{documents_id: [file1], photos_id: [file2]}`
   - Result: **2 individual files** (not catalogues, since each group has only 1 file)

**Benefits:**
- Files in same parent folder process as ONE catalogue ✅
- Each file still processes individually (gets its own transcription, etc.) ✅
- Files share catalogue output structure with their siblings ✅
- Uses proper folder processing mode instead of batch mode ✅
- Handles mixed scenarios (files + folders, multiple folders, etc.) ✅
- Temporary symlink directories automatically cleaned up ✅
