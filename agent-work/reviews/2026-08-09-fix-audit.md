## F1. `373f213ef` — the A1 sandbox gate — CORRECT

**Fixes the mechanism.** `_engine_is_sandboxed()`
(`fichero-server/src/fichero_server/security/security_scoped_access.py:171-177`)
reads `APP_SANDBOX_CONTAINER_ID`, which macOS sets in every sandboxed process
and leaves absent otherwise. That is a real kernel signal, not a constant — it
is not the `showInspectorToggle` trap one layer down.

Checked the way it could quietly fail, which is the *opposite* direction from
the security concern — a false negative would disable the fallback in the
sandboxed engine and bring back #4576. It does not: the engine spawn builds its
child environment with `childEnvironmentBase`
(`fichero/fichero/Services/EmbeddedBackendService+Tokens.swift:23-25`), which
filters only keys prefixed `FICHERO_`. `APP_SANDBOX_CONTAINER_ID` is inherited
intact, and an inherit child of a sandboxed parent would be given it by the
kernel regardless. Belt and braces.

**The four pinning tests were updated, and the consequence is written down.**
All three pre-existing fallback tests now set the container signal explicitly
with a comment saying why, and a new test —
`test_unsandboxed_engine_never_grants_via_the_probe` — pins the security
decision with the reasoning in its docstring. This was my complaint about the
original: the tests documented an undocumented decision. They now document a
stated one.

*Minor, offered not urged:* the gate is environment-derived, so if anyone ever
hardens the spawn to a scrubbed environment, the fallback silently switches off
and #4576 returns with no error naming the cause. A one-line log on the
"unsandboxed, so not probing" branch would make that failure self-describing.

## F2. `ca5bc3edf` — page focus surviving a same-document refresh — CORRECT

**Distinguishes identity from snapshot; does not merely stop clearing.** The
guard is `if oldDoc?.id != newDoc?.id`
(`Views/Shell/ContentView/ContentView+StateEvents.swift`), fed by widening the
handler to `handleDetailDocumentChange(from:to:)` and taking both values from
`.onChange(of: detailDocument) { oldDoc, newDoc in … }`
(`Layout/ContentView+RootLayout.swift:308-310`).

So #1463 is preserved exactly — a genuinely different container still clears
page focus — while a snapshot replacement of the same document does not. That is
the distinction I asked for, made at the right place. Edge cases behave:
`nil → nil` does not clear (correct, nothing changed); `doc → nil` and
`nil → doc` both clear (correct, identity changed).

*Gap:* **no test.** The lane's own rule is that every change ships with tests,
and this one is highly testable — the handler now takes both documents as
parameters, so a pure test could assert "same id keeps page focus, different id
clears it" without any view. Given this is a fix for a symptom Daniel reported
directly, a regression here would be silent and would look exactly like the
original bug.

## F3. `f4d233976` / `487601f4c` — primary selection — CORRECT BUT HALF-LANDED

And the second half — reconciling the four precedence chains — has not started.

### Why the partial state has a sharp edge

This is the specific thing I warned about, now half-realised, and the direction
is worse than it looks.

**Before the fix**, all seven sites read the same `Set` and got the same element.
The primary was *arbitrary*, but every surface agreed on the same arbitrary
answer. The preview and the inspector showed the same document — the wrong one,
consistently.

**Now**, the shell handler resolves `detailDocument` in **document order** while
`inspectorDocument` (`StateSelection:31`) and the preview
(`documentForCanvas` → `LayoutMode:295`) still resolve in **hash order**. For any
multi-selection where those differ, the preview and the inspector now show
**different documents**.

So the symptom Daniel already reports — *"the sidebar says page 7, the toolbar
says 1, the inspector shows another page"* — becomes **more** reachable in the
current state than it was this morning, not less. The fix is right and the
destination is right; the intermediate state is the one configuration worse than
either end.

**This is not an argument to revert.** It is an argument to finish: the helper
exists, it is tested, and converting the remaining five is mechanical.
`LayoutMode.swift:295` is the highest-value single line, because it feeds both
preview call sites at once — but note it is a `nonisolated static` policy
function taking `selectedDocumentIds` and `documents`, so it can call the same
helper directly without a plumbing change.

Recommend finishing the five before this lane is called done, and only then
taking the precedence chains as the separate design piece they are.

## F4. `6f5826977` — right-click targets the clicked row — CORRECT

`selection.contains(document.id) ? Array(selection) : [document.id]`
(`Views/Library/LibraryView+ContextMenu.swift:394-401`). This is the Finder rule
and it now matches the file's other resolvers.

Checked the one-row edge: when the clicked row is the *only* selected row,
`Array(selection)` and `[document.id]` are the same list, so the absence of the
`selection.count > 1` clause that `imageStackTargets` carries is not a
behavioural difference — just a shorter way to say it.

*Gaps:* **no test**, and the deeper finding is deliberately deferred. The commit
message is honest about it ("four hand-written answers to one question — that is
task #11's contract work; this aligns the one that disagreed"), which I think is
the right call for tonight. But the class remains: there are still four
resolvers, and nothing stops a fifth. The shared `contextMenuTargets(clicked:)`
plus a pin test is what actually closes it.
