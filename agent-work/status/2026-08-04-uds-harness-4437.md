# #4437 — the headless UDS harness is already restored, and that is the problem

**Reading + verification only. Nothing deleted, no default changed.**

## Short answer

`#4437` was landed earlier tonight (`f915441f7`) and **works**: the harness runs
headlessly, spawns a real uvicorn on a real Unix socket, drives real httpx
requests, and **provably detects a dead socket**.

But it should probably not be wired into the gate, because **the gate already
runs the same coverage from a different file** — and that file was *recovered
from this very harness* precisely because standalone assets outside the gate do
not get run.

Restoring the standalone copy re-created the condition that stranded it.

## What existed, and why it went

`fichero-server/tests/integration/test_transport_round_trips.py` says so itself:

> Recovered from the stranded `transport-tests/` harness (`3a638470f`), which was
> written as standalone assets for a manager to integrate later and never was.

So the sequence is:

1. `transport-tests/` written standalone. Never integrated. Stranded.
2. Its content recovered into `fichero-server/tests/integration/`, which **is**
   in the gate (`scripts/gate:89`, `cmd_transport`, #4245) — and widened from UDS
   alone to **UDS + HTTPS + in-memory**.
3. #4437 restored the standalone `transport-tests/` copy.

**The reason it went still holds**, and it is not "the harness was bad" — it is
"standalone assets nobody runs do not protect anything". That reason was fixed by
recovery, and the restore undid the fix by re-adding the unrun copy.

## Verified, not assumed

| what | result |
|---|---|
| `transport-tests/pytest/test_uds_roundtrip.py`, live | **`4 passed`** |
| the same file, socket unlinked after readiness | **`4 failed`** |
| `fichero-server/tests/integration/test_transport_round_trips.py` | **`7 passed`** |
| anything in `scripts/`, CI, or pytest config referencing `transport-tests/` | **nothing** |

**The detector proves it can see the bad case.** I sabotaged `_engine_harness`
to unlink the socket immediately after the readiness probe, ran the real test
file, and got 4 failures where a live socket gives 4 passes. A harness that
passed on a dead socket would be worse than none; this one does not.

It also fails *loudly* rather than skipping: a dead engine raises `RuntimeError`
or `TimeoutError` out of `start_engine`, so the fixture errors. There is no skip
path anywhere in `transport-tests/`. That matters — a skip would read as a pass.

## Headless: yes

No GUI session, no window server, no app. It spawns
`uvicorn fichero_server.api.uds_transport:app --uds <tmp>` as a subprocess and
talks to it over `httpx.HTTPTransport(uds=...)`. Whole run is ~4 seconds. This is
**not** blocked by #4511, which concerns the Swift unit-test host.

## One factual error in the restored file

Its comment says:

> The original `/api/actions/registry` no longer exists.

**It does exist** — `fichero-server/src/fichero_server/api/routes/system/actions_registry.py:167`.
The gated suite still asserts against it and passes. The harness switched to
`/api/settings/model-profiles` for a stated reason that is untrue. The test still
passes, because the substitute endpoint is also valid — so nothing is red, and a
reader would simply believe an endpoint had been removed when it had not.

Corrected in place rather than left, since it survives either decision below.

## Recommendation — team-lead's call

**Do not wire `transport-tests/pytest/` into the gate.** Two suites asserting the
same three things about UDS, with nothing forcing them to agree, is the defect
class removed five times tonight. The gated one is strictly broader.

Two honest options:

1. **Delete `transport-tests/pytest/test_uds_roundtrip.py`** as superseded, and
   keep `transport-tests/` for `profile_transports.py`, which is genuinely
   unique — the gated suite asserts correctness, not latency.
2. **Keep it as a documented manual probe**, with the header now pointing at the
   gated suite as the thing that actually runs.

I did not delete it. It was restored deliberately hours ago and deleting it the
same night on my own reading is the kind of move that should be someone's
decision, not a lane's.

## What this does NOT settle

The transport question from #4486 is still open. This harness proves the
**engine** serves UDS correctly. It says nothing about whether a `claim.updated`
event reaches the **Swift** client — that hop needs the queued Swift test, and
#4511 currently blocks executing it.

Transport profiling (`profile_transports.py`) was not run or reviewed: scope was
round-trip first, and the round trip turned out to be a map rather than a build.
