## 1. What the backlog actually is (assume it lies)

**745 issues open.** By creation date: 362 from June or earlier, 383 from
July/August. Two different populations:

- **June and earlier (~360)** is mostly roadmap seeding — 275 were filed in
  June alone. The Library & Reading milestone holds 65 open issues of which
  **one** was filed since June, and three separate lanes plus the standing
  memory note ("Library & Reading Surface mostly implemented — triage before
  implementing") have found this population largely built-but-never-closed.
  34 were closed exactly that way in one evening on 07-30.
- **July/August (~380)** was filed from real use of the app. These are live —
  but ~60 of them are already fixed and commented with SHAs, awaiting
  Daniel's Tuesday verify-close.

**Estimate of real, distinct, still-valid work: 250–350 items**, arrived at by
applying the observed already-fixed rate (roughly half) to the pre-July
population and subtracting the fixed-awaiting-verify tail from the July one.
And of those, the top handful of *programs* (section 3) absorb well over a
hundred issue numbers. A plan that treats 745 issues as 745 pieces of work
would spend the week closing phantoms one at a time.

**Consequence:** verify-close sweeps are among the highest-yield work
available, at near-zero risk, needing no build. A triage lane closing
20 phantoms a day is worth more than a coding lane fixing 3 real bugs — and it
shrinks every future plan.

Nearly every defect Daniel personally hit this week was "two or more

and every fix closes a cluster.

Order inside the program (from the issue, confirmed by this week's evidence):
1. Build the surface × interaction table BEFORE fixing anything (#4412 proved
   this finds unreported defects immediately). The table is a committed
   deliverable, not scratch.
2. Document-inspector lists (Daniel names a live defect: unclickable icons,
   dead operations).

   *outcome* (file location + DB row), since #4401 already caught "move"
   silently copying.
4. Then column-by-column: one shared implementation per interaction, tests
   per cell.

## 4. What should NOT be attempted (and why)

- **#4463's sync half.** Daniel's own framing says it: today's model is one
  server-authoritative writer; iCloud sync is two writers reconciling later —
  **a second consistency model, not a fifth transport**. Approached as "the
  same app over iCloud" it eats a year and corrupts databases. The only
  legitimate work this week is the design pass answering the issue's five
  questions, with the strong prior already in the issue: managed-mode-first
  (useful alone, single-writer intact), sync-as-append-only-intent-log if
  ever. Any lane that starts writing sync code is stopped on sight.
- **PythonKit-on-iOS as a foundation for anything.** #4331's class of crash
  (1 MB stacks, load-bearing AnyViews) says the iOS story is still settling.
  Verify the TestFlight build launches (Daniel, Tuesday); build nothing on it.
- **Reader View implementation** — the standing note is explicit: #3765's plan
  is confused and needs a design pass first. Audit yes, code no.
- **Client-Web, visionOS, Static-Site milestones** — vision, not this week.
- **Wholesale hygiene/rename passes** while three-plus lanes are in flight;
  every rename breaks path-keyed guardrails and invites the #2566 shim class.
  Hygiene comes after DMG+TestFlight per the standing order (#2569 first).
- **Anything requiring a decision on Daniel's list** — #4460 (shift-click
  order on canvas), #2440 (which palette), #3961 (delete or keep
  DocumentHierarchy) are blocked-on-Daniel by definition; don't guess them.
