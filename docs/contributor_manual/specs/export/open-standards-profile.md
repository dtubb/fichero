## Intent

**Fichero is the editor. The web is a static rendering.** Everything a project knows — its images, segments, readings at every level, orders, notes, hands, claims, catalogue fields, rights, the models that read it and the runs that made each thing — leaves Fichero as ONE bundle that speaks open standards, and comes back in with nothing lost. Every other output (a site, a workbook, a BibTeX file, a Word transcript, a training set) is a VIEW derived from that bundle, never a parallel format with its own idea of the data.

The standards are the existing ones, used as published, never a dialect of our own: RO-Crate for the bundle, IIIF Presentation 3 and Image API 3 for images and their canvases, W3C Web Annotation for everything said about a canvas, RDF (JSON-LD, schema.org context) for the graph, PROV-O for who or what made each thing, CSVW and Parquet for the tables, Dublin Core and schema.org for the catalogue, CSL JSON / CITATION.cff / BibTeX for citation, SKOS for the reference lists, PAGE XML / ALTO / TEI / SVG / Markdown as page views, Croissant and model cards for training sets and models.

## Rulings (owner, 2026-11-08, from #6439 and its comments)

1. **One bundle, many views.** The bundle is the canonical exchange format. The existing BibTeX exporter, the catalogue workbooks, Word, Markdown and the Eleventy site are DERIVED VIEWS of it, not parallel formats: they read the same stream and the same ids.
2. **Order of writing:** (1) bundle + round-trip, with tables and catalogue; (2) Markdown and the page views; (3) Publish, with citation data; (4) deep links; (5) training sets, Croissant, model cards; (6) import, with BibTeX/BibLaTeX import.
3. **Publish** writes a DATA FOLDER and a SITE CONFIG for a website whose template, viewer and build live in their OWN open-source repository (own licence; Eleventy, Mirador or OpenSeadragon, MapLibre), buildable and viewable with no Fichero code or service; Fichero can push to a static host. Per-item rights and licence are shown; the open data bundle is downloadable from the site; deep links open the app only when it is installed, a plain link otherwise.
4. **No new API where one fits.** Reuse the record stream, the page exporter, the IIIF routes, the KG RDF export, the catalogue columns, the kept exports and the format harness. **Spec only, no code; not in the dev build.**
5. **Lossless round trip is the test**: a library exported, imported into a fresh library and exported again gives the same bundle.
6. **Private and public are respected throughout** (confirmed 2026-11-08): per item, per reading, per entity; nothing private leaves, and a statement is public only if its sources are. The gate is the exporter's existing one, applied once.
7. **The published site has** entities, statements (subject, verb, object), dates, places, readings and translations (confirmed); **GitHub Pages and Netlify are first-class targets**, as is any folder.

## The profile, by layer (the map)

One row per layer: what is exported, the standard it speaks, the existing piece that produces it today, and the view derived from it. The bundle's folder names are in the first column.

| Bundle part | Standard | Produced today by | Derived views |
|---|---|---|---|
| `ro-crate-metadata.json` | RO-Crate 1.1 (JSON-LD, schema.org) | nothing (the one new emitter, over `iter_export_records`) | every view reads it for ids and parts |
| `images/` | the files, or IIIF Image API 3 URLs by reference | the library's originals and renditions; `iiif.export.points-at-original` | the site's tiles (level 0), thumbnails |
| `iiif/` | Presentation 3 manifests and collections | `GET /api/iiif/iiif/manifest/{document_id}` (per document; folders not built) | the site's viewer, "Copy IIIF Link" |
| `annotations/` | W3C Web Annotation pages | `GET /api/iiif/iiif/lines/{document_id}` (working pass's lines; other readings, notes, claims not built) | the site's transcription beside the image |
| `graph/` | RDF: JSON-LD (schema.org context) + PROV-O | `GET /kg/export/rdf` (entities, claims; no attribution today) | person and place pages, SPARQL elsewhere |
| `tables/` | CSVW (CSV + `csv-metadata.json`) and Parquet | `export_parquet` through DuckDB; the record stream's columns | the catalogue workbook, Excel, the HF dataset |
| `catalogue/` | Dublin Core terms + schema.org, and the IIIF manifest's `metadata`, `rights`, `requiredStatement` | the catalogue attributes and prototypes (`catalogue.export.template-is-the-prototype`); `iiif.rights-travel` | the workbook's rows, the site's document pages |
| `views/` | PAGE XML, ALTO 4.4, TEI, SVG, Markdown, plain text; a DuckDB file | `page_export.export_page` through the formats registry (SVG, Markdown-per-page and DuckDB not built) | the synced folder, Word, "Export Page As" |
| `citation/` | CSL JSON, CITATION.cff, BibTeX/BibLaTeX | `bibliography/importers.py` (`write_bibtex`, `read_csl_json`), `POST /api/bibliography/export.bib` | cite-this-page, the site's meta tags |
| `reference/` | SKOS (RDF) or CSL JSON | the gazetteer and name list (`../kg/project-gazetteer-and-names.md`) | the site's search index |
| `training/` | Croissant (JSON-LD) + model cards | `training/kraken_set.py`, `training/line_pairs.py`, `recipes/cards.py` (no Croissant, no card file) | the HF dataset bundle (`export.huggingface-dataset-ready-bundle`) |
| `fichero/` | the choices and the id map (JSON) | `page_export.ExportChoices`; `fichero:segment/…` references (`SegmentReference`, `POST /api/locations/resolve`) | deep links, re-import matching |

## Behaviors

Part 1 — the bundle and its round trip, with the tables and the catalogue (#6439, owner order (1) and addition (a), (b)).

- `profile.editor-not-the-web` — **[GAP]** (#6439, ruling 1) Fichero is the editor and the only writer; everything outside it is a rendering of the bundle. Nothing on a published site, in a workbook or in a view writes back into the project except through an import (Part 6) or a community note for review (`site.community-notes`). Acceptance: no export surface carries a write-back URL to the engine; the site's config names the bundle as read-only data. *Test:* `test_profile_views_are_derived_6439.py` (not yet written; every emitter reads the stream and the same ids, none holds a second model of a record).
- `profile.private-never-leaves` — **[GAP]** (#6439, ruling 6) the bundle, and every view derived from it, carries ONLY what is public to the scope exported: the one filter in the record stream (`source.format.rights-filtered-once`) applies the exporter's existing gate, the export routes' reads check over every document named (`assert_library_reads_every`, `documents_under` in `api/routes/ingest/export.py`) and the rights record's per-item answer (`source.rights.record`, `source.rights.exports-leave-out`), extended to readings and entities: a PRIVATE reading (a level, a person's note-reading, a reading marked private) is not written to any part, not even as a count; a STATEMENT (claim) is written only when EVERY source it rests on is public, the rule the entity and claim reads already apply (`source.rights.claims-with-only-denied-evidence-are-hidden`), and a statement with one public and one private source goes out with the public evidence only; an ENTITY reachable only through private items (every mention, every statement private) is dropped from `graph/`, `tables/entities.csv`, `reference/` and the crate, with no placeholder and no `withheld` count in the bundle. The site's data folder (Part 3) is built from the bundle, so it can hold nothing the bundle does not. Acceptance (the fixture of Step 1.5): a private page leaves out its statement; an entity mentioned only on that page is absent from every part; a private reading never appears in `annotations/`, `views/` or `tables/readings.csv`; the public statement with a private second source lists the public source alone. *Test:* `test_bundle_keeps_private_in_6439.py` (not yet written; the three absences and the one trimmed statement, by grep over every file of the bundle), the existing `test_holds_close_6320.py` and `test_read_exports_check_the_body_ids_6320.py`.
- `profile.bundle.is-an-ro-crate` — **[GAP]** (#6439) a project, a folder or a selection exports as ONE bundle, a folder or its zip, that is a valid RO-Crate 1.1: `ro-crate-metadata.json` at its root (JSON-LD on the RO-Crate context plus the schema.org context the KG export already uses), the root `Dataset` naming the scope (its title, the catalogue's description, `license`, `datePublished`, the Fichero version and the engine identity as `sdPublisher`), one `File` or `Dataset` entity per part with `encodingFormat` and `conformsTo` (the IIIF, Web Annotation, CSVW, PROV-O, PAGE, ALTO, TEI profile URIs), and `hasPart` listing every file written; nothing is in the folder that the crate does not describe, and nothing the crate describes is missing. The crate is written by ONE new emitter beside the others, `export_ro_crate` in `export_service.py`, over `iter_export_records` and the page exporter, and it is reached as a KEPT EXPORT format (`/export/kept`, format `bundle`, one folder per project, rewritten when the project changes) and as the one-shot "Export Bundle…" that keeps and writes once to a chosen folder; no new route. Acceptance: a project's bundle validates with the RO-Crate validator and with the JSON-LD expand/compact isomorphism check the KG export already runs; every file in the folder is in `hasPart`. *Test:* `test_bundle_is_a_valid_ro_crate_6439.py` (not yet written; the crate's shape, `hasPart` equals the folder's files, the validator), the existing `test_export_service.py` and `test_catalogue_workbook_kept.py`.
- `profile.ids.one-id-everywhere` — **[GAP]** (#6439) every thing in the bundle has ONE stable identifier used in every part: the segment reference as the app writes it (`fichero:segment/<library>/<document>/<segment>`, `SegmentReference`), and the same shape for documents, readings, orders, entities, claims, runs and people (`fichero:<kind>/<library>/…`); when the scope has a publish base URL (Part 3) the crate also states each id's `https://…/id/<kind>/…` form as `sameAs`, so the site, the manifests, the annotations, the RDF and the tables all name the same thing by the same string; PAGE and ALTO carry the ids as today (`source.sync.files-carry-ids`). An id is never re-minted on export: exporting twice gives the same ids. Acceptance: a line's id in `annotations/`, `tables/segments.csv`, `views/<page>.xml` and `graph/` is one string; a resolve of it (`POST /api/locations/resolve`) lands on the live segment. *Test:* `test_bundle_ids_are_one_string_6439.py` (not yet written; the id of one segment read from four parts), the existing `test_segment_references.py`.
- `profile.provenance.prov-o-on-everything` — **[GAP]** (#6439) every reading, segment, order, claim, catalogue value and image rendition in the bundle says who or what made it, in PROV-O: `prov:wasAttributedTo` a `prov:Person` (the account, by its public name) or a `prov:SoftwareAgent` (the model by its card id `<runtime>:<source>@<version>`, `source.model.card-id`), `prov:wasGeneratedBy` a `prov:Activity` for the run (its recipe step, start and end, the settings that matter: temperature, prompt id, level), and `prov:wasDerivedFrom` what it was made from (the rendition read, the earlier reading corrected, the teacher's line); the source is the record's attribution chain (`_made_by` in `export_service.py`, the readings' `created_by`/`read_from`/run). The STORED value goes out under its own name and a derived value under a clearly separate one, never substituted (the ruled direction in `exporter.md`'s design note). PROV travels in `graph/provenance.jsonld` on a second named context (`prov`), referenced by id from every part, and as each W3C annotation's `creator` and `generator`. Acceptance: a machine reading corrected by a person exports as two readings, the machine's attributed to the model's card id and generated by its run, the person's attributed to the person and derived from the machine's. *Test:* `test_bundle_provenance_is_prov_o_6439.py` (not yet written; the two readings and their three PROV relations; the stored value named as stored), the existing `test_jsonld_export.py`.
- `profile.tables.csvw-and-parquet` — **[GAP]** (#6439, addition (a)) `tables/` holds the record stream as TABLES twice over, the same rows and columns: one CSV per record type (documents, pages, segments, readings, orders, entities, claims, mentions, runs, catalogue) with ONE `csv-metadata.json` (CSVW: each table's `tableSchema` with typed columns, `primaryKey`, `foreignKeys` between the tables by the one id, `aboutUrl` the id's URL form), and the same tables as Parquet through the existing DuckDB writer (`export.duckdb-parquet-not-pyarrow`), one file per table, never PyArrow. The catalogue workbook (`catalogue.export.*`) and the Excel emitter are derived from these tables: their columns are the catalogue table's columns under the prototype's labels (`catalogue.export.template-is-the-prototype`), so a cell in the workbook and a cell in `tables/catalogue.csv` are one value. Acceptance: `csv-metadata.json` validates as CSVW; `readings.csv`'s `segment_id` is a declared foreign key to `segments.csv`; the Parquet `segments` file has the CSV's rows; a workbook built from the same scope has the catalogue table's values cell for cell. *Test:* `test_bundle_tables_are_csvw_and_parquet_6439.py` (not yet written; the schema, the keys, CSV equals Parquet, workbook equals table), the existing `test_export_service.py` and `test_catalogue_sheet_rows.py`.
- `profile.catalogue.dublin-core-schema-org-and-iiif` — **[GAP]** (#6439, addition (b); fits `catalogue.export-standards`, #5365) each document's catalogue entry is written once in `catalogue/<document>.jsonld` as Dublin Core terms (`dcterms:title`, `creator`, `date` as EDTF, `description`, `extent`, `language`, `rights`, `accessRights`, `isPartOf`, `identifier`) and schema.org (`ArchiveComponent`/`CreativeWork` with `holdingArchive`, `locationCreated`, `about` for the people and places by their graph ids), mapped from the catalogue attributes by their prototype's declared mapping (the mapping is data on the prototype, never a switch in code); the SAME values appear as the IIIF manifest's `metadata` (label and value pairs in the project's languages), `rights` (a URI from the rights record, `source.rights.record`), `requiredStatement` (the attribution the archive asks for) and `provider`, so the manifest and the catalogue file never disagree. Restricted material is left out ONCE, in the record stream (`source.format.rights-filtered-once`, `source.rights.exports-leave-out`): a withheld document has no catalogue file, no manifest, no rows and no count anywhere in the bundle. Acceptance: a catalogued document's title, date and rights read the same from `catalogue/<id>.jsonld`, its manifest and `tables/catalogue.csv`; a restricted document is absent from all three and from `hasPart`. *Test:* `test_bundle_catalogue_is_dc_and_schema_org_6439.py` (not yet written; the mapping from one prototype, the three places equal, the restricted document absent), the existing `test_catalogue_sheet_template.py` and `test_iiif_by_reference.py`.
- `profile.round-trip.export-twice-is-identical` — **[GAP]** (#6439, ruling 5, the first half) exporting the same scope twice, with nothing changed between, gives two bundles that are byte-identical apart from `datePublished`; every file validates against its schema or profile (the formats registry validates each page view as today, `source.format.export-validated`; the crate, the manifests, the annotation pages and `csv-metadata.json` against their JSON schemas kept on disk, `source.format.schemas-on-disk`, never fetched); every loss is DECLARED in the crate (a `fichero:loss` list per file from the formats' `LossReport`, `source.format.loss-report`), never discovered. The second half, import of a bundle into a fresh library and re-export giving the same bundle, is Part 6 (`profile.round-trip.lossless`); the test file is written in Part 1 with this half and gains the second half there. Acceptance: two exports of a fixture library differ only in the date; a TEI view's declared losses are listed in the crate beside the file. *Test:* `test_bundle_round_trip_6439.py` (not yet written; the two exports compared, every file validated offline, the losses listed), the existing `test_pagexml_round_trip.py` and `test_export_validation.py`.

Part 2 — the page views: Markdown, PAGE, ALTO, TEI, SVG, plain text, DuckDB (#6439, owner order (2)).

- `profile.views.every-view-is-a-page-export` — **[GAP]** (#6439) `views/` is written by the ONE page exporter and nothing else: each page becomes a `SourcePage` once (`page_export.page_from_library`, with the bundle's choices: pass, order, reading kind and level, `source.format.export-choices`) and every format in the registry writes from it (`formats.write_page`: PAGE XML, ALTO 4.4, TEI, hOCR, YOLO today; SVG, Markdown and plain text join the registry below), one file per page per format, validated against its schema (`source.format.export-validated`), its losses declared (`source.format.loss-report`) and listed in the crate. The kept page exports and the synced folder (`source.sync.out-is-the-exporters`) are this same writer, so a kept bundle's `views/` IS the synced folder of its project; nothing renders a page twice. Acceptance: `views/<page>.xml` (PAGE) from the bundle is byte-identical to the kept PAGE export of the same page with the same choices; a format with no slot for a field lists the loss in the crate. *Test:* `test_bundle_views_are_the_one_exporter_6439.py` (not yet written; bundle view equals kept export; the loss listed), the existing `test_page_export_route.py` and `test_export_validation.py`.
- `profile.views.markdown-is-plain-and-round-trip-ready` — **[GAP]** (#6439; the contract of #3176, narrowed) Markdown is PLAIN CommonMark a person can read and edit: one file per page and one per document (the pages as second-level headings, as `render_markdown_text` writes today: a line per line with the hard break, a line that begins like a heading or list escaped, never re-shaped), with a SHORT front matter — `id`, `title`, `parent`, `order`, `pass`, `level`, `editable: [body]` — and NO ids inside the text: the crate's id map ties the file to its page and each body line, by its order in the file, to its segment, so an edited line comes back as a correction of that segment (Part 6) and a reordered or added line is said, not guessed. Markdown is a registered format (write and read) in the registry, so it is validated (front matter parses back to what was written, `source.format.export-validated`) and its loss report names what Markdown cannot hold (geometry, hands, marks, other readings). The Reader's client-side "Export as Markdown" (`export.app-wires-word-and-per-document-markdown-only`) stays as the quick copy of the text on screen; the bundle's Markdown is the engine's. Acceptance: a page's Markdown has its front matter and one body line per line in reading order; parsing the file back gives the same front matter and the same lines; the crate maps line 3 of the file to the third segment in that order. *Test:* `test_bundle_markdown_is_plain_and_mapped_6439.py` (not yet written; the front matter, the lines, the map, parse-back), the existing `test_export_service.py` and the kept Markdown test of #5502.
- `profile.views.svg-page` — **[GAP]** (#6439; `source.format.svg-out`, #4946) each page is written as SVG from the same `SourcePage`: the page image as `<image>` (a relative path into `images/` or the IIIF Image API URL when by reference), the page's pixel grid as the `viewBox` (`formats.harness.pixel_grid`); each region a `<g>` whose `id` is its Fichero id with its polygon as `<path>`, each line inside it a `<path>` for its baseline and a `<text>` set along it with `<textPath>` (the counting reading at the chosen level), `direction` and `writing-mode` from the line's direction, `xml:lang` from its language and script; a description segment gives `<title>` and `<desc>`. A write-only format in the registry (the registry allows a writer without a reader, `FormatCannotRead`), validated against the SVG 1.1 schema kept on disk, its losses declared (hands, marks, other readings). Acceptance: a page with two regions and five lines writes an SVG with two groups, five text paths along five baselines, the right-to-left line's `direction="rtl"`; the file validates offline. *Test:* `test_svg_view_6439.py` (not yet written; the groups, the paths, the direction, validation), the existing `test_harness.py` and `test_right_to_left.py`.
- `profile.views.plain-text-and-duckdb` — **[GAP]** (#6439) two conveniences, both derived and both declared as such in the crate (`conformsTo` none, `fichero:derivedFrom` the part they come from): plain text per page and per document, the page's derived text in reading order with furniture left out, exactly the kept plain-text export (`document_text`), and ONE `views/library.duckdb`, a DuckDB database whose tables are `tables/` loaded as written (the Parquet files read into tables of the same names through the managed connection, as the Parquet writer runs, never a second query of the library), read-only for analysis in DuckDB, Python or R. Neither is a source for import: Part 6 reads the crate, the tables and the views, never the text file or the database. Acceptance: `views/library.duckdb` has a `segments` table with `tables/segments.parquet`'s row count; the plain text of a page equals the kept plain-text export of it. *Test:* `test_bundle_plain_text_and_duckdb_6439.py` (not yet written; the row counts, the equality, the crate's derived marks), the existing `test_export_service.py`.
- `profile.views.levels-and-translations-have-a-place` — **[GAP]** (#6439; with `source.editor.levels-section-and-working-text`, #6429) every reading level and translation a segment has reaches the views where the format has a place for it, and is a declared loss where it has none: TEI carries the levels in `<choice>` (`<orig>` the as-written, `<reg>` regularised or modernised, `<expan>` expanded, each with `@resp` pointing at the PROV agent) and a translation as a parallel `<text xml:lang>` joined by `@corresp`; PAGE XML and ALTO hold one level per file, so the bundle writes one file per level asked, named with the level's suffix, the working text's file unsuffixed; Markdown and plain text write one file per level the same way; the annotations part (Part 1) carries every level as its own labelled annotation page already. The bundle's default is the working text plus every level the scope has readings at; the choice is in `fichero/choices.json`. Acceptance: a line with as_written, modernised and a translation exports a TEI with a three-way `<choice>` and a parallel text, two PAGE files (working text, modernised), and the loss report of hOCR naming the levels it dropped. *Test:* `test_bundle_levels_in_the_views_6439.py` (not yet written; the TEI choice and parallel text, the files per level, the declared loss), the existing `test_tei.py` and `test_reading_levels.py`.
