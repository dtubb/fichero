# Engine silent failures: what the logs say, and how to catch them

> **Status: DRAFT, 2026-10-30; revised against the code 2026-10-31.** Owner's order (2026-10-30): the engine must be
> rock solid, so silent failures need a way to be caught, specced, tested against spec and fixed, as the UX's stall
> detector does for slowdowns.
> Manual: TBD — a "When something keeps failing" section: what the amber engine pill and an Activity "Needs attention"
> row mean, and what Reconnect does for originals on another volume.
> Tags: **[OK]** behaves this way today · **[PARTIAL]** part built or not wired · **[GAP]** intended, not built.
> Every non-[OK] bullet cites an issue. #4420 (closed; the seam programme) stands in for the bullets that have no issue
> of their own yet: the lead files the titles under "Issues to file" and replaces the number.
> Part 1 is the inventory (what the two real logs say). Part 2, "The detector", is the spec, each bullet tagged with
> what is built. A `file:line` in the inventory table is from the logged build; elsewhere a bullet names the function or file, not a line, because lines move.

## What the inventory says

* **Three of the top six lines are one failure with three causes**: the embedder cannot load, and every document
  write retries it, logs a line and moves on. 389k lines in 38 hours on the Air. The code already knows the difference
  (`EmbedOutcome.reason` = `embedder_unavailable`, #4395) and the queue "waits and says why" (comment at
  `db/__init__.py`, `Database.embed`); the line is written by the *caller of each write*, so the wait never reaches the log as one
  line, the log as a rate, or health as a state.
* **The engine already has the seams for "say it once, in a place a person looks"** (`startup_warnings.py` into
  `/api/health` `dependencies`, the swallowed-exception seam baseline, the stall watchdog); none of them counts a
  repeated WARNING, and the app reads `dependencies` only for the About box's versions and the previous stall
  (`fichero/fichero/App/AppState/AppState+HealthCheck.swift:87-92`): a `failed: <Class>` entry is shown nowhere.
* **Much of the Air's log is INFO that would hide any real signal** (5 of the top 10 templates): this is the log-collapse worker's
  (branch `feat/logs-stale-servers-support`) ground; this spec only counts WARNING and above (see Part 2).
* **The engine's log set-up is not `core/logging.py`**: the handlers that write `engine.log` come from
  `logging.basicConfig` in `fichero_server/__main__.py:35` (root logger, format `asctime - name - levelname - message`;
  the app captures stdout/stderr into the file). `core/logging.py`'s `configure_logging` is called nowhere in
  `fichero-server/src`. The collapse branch adds `engine_log.start` to `__main__.py` and collapses per call site
  (`core/log_throttle.py::log_collapsed`), not with a handler. This decides open question 1.

## The classes (one bullet each; ids are `engine.silent.<slug>`)

Each class names **the test that proves the failure is surfaced** (`Test:`) and **the fixture log** that test and
`scripts/scan_engine_log.py` read (`Fixture:`). A bullet tagged [OK] must name a test file that exists; the guard is
`tests/unit/seams/test_engine_silent_spec_names_tests.py` (`engine.silent.every-bullet-names-its-proof`). "Surfaced"
means one of: a `degraded` entry in `/api/health` with a sentence, a reason in the endpoint's 404 `detail`, or a worded
row in Activity; a log line alone never counts.

- `engine.silent.embedding-fails-every-write` — **[PARTIAL]** (#4395 open, "Embedding failures are swallowed"; #6218 closed, the forked child dies while it downloads; #1524 closed, bge-m3 not supported) an embedder that cannot load makes every document write log one WARNING (389k on the Air) and produce no vector; health says `healthy`, Activity says nothing, Search silently loses the pages. Built 2026-10-30: `Database.embed`'s `except` calls `failure_ledger.note("search", "embed", <cause class>, sentence=...)` (`db/__init__.py`, in `Database.embed`) and `/api/health` lists "Search is not indexing new pages: the search model cannot be loaded (EmbedderUnavailable). 25 failures since 09:19." (the class is `EmbedderUnavailable`, which `embeddings.py` and two of `embed_process.py`'s raises (a load timeout, the model's own failure words) give no `from`, so those causes share one signature; a dead child raises `from` the `EOFError`/`OSError`, so its reason says that class instead; the words that tell them apart stay in the engine log, not on health) Unbuilt: the Swift rows (`app-says-degraded`), and "N pages waiting" (the ledger counts failures; the queue's own count is #4395's). Test: `tests/unit/core/test_failure_ledger.py::test_embedding_failure_degrades_health` (built: 25 failing writes, one `search` entry, no path in the reason). Fixture: `tests/fixtures/engine_logs/embedding_380k.log` (the real line shape, both causes; read by the scan test).
- `engine.silent.change-hub-key-drift` — **[PARTIAL]** (#2518 closed, #6309) both hub seams (subscribe, unsubscribe, emit) call ONE function, `canonical_library_key` (`db/library_paths.py`: NFC like `DatabaseManager`, then `realpath`), so an accented name in the form macOS hands a window and the form the engine opens reaches the same subscribers. An emit that reaches 0 subscribers while other libraries are live (a real second library, e.g. `Project.fichero` with no window next to an open `Project 12.fichero`, is not a spelling drift) warns once per key pair and again at 10, 100, 1000 ... with the count (`api/change_stream.py`, `_ChangeHub.emit`), not once per event. Unbuilt: the ledger entry (area `live-updates`) and the Activity words. Test: `tests/unit/api/test_change_hub_key_drift_is_degraded.py::test_accented_name_in_either_unicode_form_reaches_the_window` and `::test_drift_warns_once_per_pair_with_a_count`. ## The originals class (added 2026-10-30, from the Air)

`engine.silent.originals-unreachable-shows-thumbnail`: after the app was replaced by a new build, the Project source
images (61k pages, originals under `/Volumes/Archive/Originals/…`, display copies and library on
`/Volumes/Work/Libraries/Project.fichero`) "need to be reconnected" and the app shows the thumbnail
instead of the original.

**What the code does today** (read, not run):

1. The fallback to the thumbnail is `fichero/fichero/Views/Preview/DocumentCanvas.swift:227-257`: when the display
   image fails to load (`loadError`) and a cached thumbnail exists, it draws the thumbnail with a capsule "Showing
   thumbnail — original unavailable" and a Retry. (The maintainer asked on 2026-08-20 for the thumbnail to load and, when the
   original is missing, a brief flag.) So it is **not totally silent**, but the banner (a) does not say why, (b) offers
   only Retry, which cannot help when access is not granted, (c) is on the Preview canvas only: the grid, the Reader
   and every other place a thumbnail stands in (`LibraryImageView.swift:79`, `seedFromCache`) say nothing, and
   (d) a thumbnail is also what a *generated* grid tile is, so a person cannot tell "this is the small copy" from
   "this is all I could get".
2. The engine's answer carries no reason: `/api/display/{id}` returns "Display image not available"
   (`api/routes/system/storage.py:286`), `/api/source/{id}` "Source file not available" (`:341`, `:345`; the cause
   goes to a WARNING with the path), `/api/thumbnail` "Thumbnail not available" (`:225`); `get_display`/`ensure_display`
   return `None` when `resolve_source` (`db/storage.py:471-499`, `candidate.exists()`) finds nothing: **"not mounted",
   "not found there" and "this engine may not read it" are the same `None`**. The classifier already exists, for the
   export only: `export_service._why_image_unavailable` (`:2027-2041`: `FileNotFoundError` → "moved or deleted",
   `PermissionError` → "grant access to its folder", other `OSError` → "may not open files in that folder").
3. The app's grants: `FolderAccessManager.resendAllGrantsToEngine` (`fichero/fichero/Services/FolderAccessManager.swift:412`,
   filter at `:419`) and `engineBookmarkPayload` (`:187`, filter at `:193`) send **only the bookmarks that cover a
   library** (`grantCoversALibrary`, `:454`, from #5228/#5251, 2026-09-28, "folders from long-closed libraries ... were
   sent one request at a time"). `restoreBookmarks` (`:460`) deletes a bookmark that fails to resolve after one
   `logger.error` whose path is `<private>` (`:513-517`); the engine's refusal is logged the same way (`:364`).

**The cause the Air's `engine.log` supports** (streamed, not copied; the Air's stored bookmarks were read with
`plistlib`, keys only):

* Until 2026-09-29 each spawn said "Security-scoped access: **10 of 10** librar(ies) granted" and listed
  `/Volumes/Archive/Library/Series 1 … Series 8`.
* From 2026-10-28 every spawn says "**3 of 3**" (`…/Libraries`, `Project.fichero`, `Project 12.fichero`): the
  folders holding the originals (`/Volumes/Archive`, `/Volumes/Archive/Originals/Series 1/Box 12`)
  are **still stored** as bookmarks in the app's defaults (18 keys on the Air) but are **not re-sent at spawn or in the
  post-ready sweep**, because no library path lies under them. A link-mode project's originals sit outside every library by design.
  They were granted only at the moment they were chosen in a session (10-28, 10-29: "granted via inherited sandbox
  scope"), and that grant ends with the engine process.
* On 10-29 10:44 the Word export then failed 1,486 times with "Export image source missing … **this engine may not
  open files in that folder: grant access to the folder**" for `/Volumes/Archive/Originals/…`:
  that is the real cause **in the engine's own words**, for the export path; the display path swallows the same
  condition into `None`.
* The log has no `Operation not permitted`, `Errno 1` or `PermissionError` line (0 hits on both machines): the engine
  never raised a permission error. `os.stat` on a path outside the sandbox without a scope gives `ENOENT`-like
  "not found", which `resolve_source` treats as "moved". **The failure is therefore indistinguishable from a missing file at every layer** until it is asked.
* **Not proven, flagged as the open question:** that the *replace of the app* is the trigger. The evidence says "a
  fresh engine process re-grants libraries only"; a replace restarts the engine, so it would show up on the first launch
  after one, but any restart does the same. Whether the app-scoped bookmarks themselves still resolve after a replace
  with a new build (same bundle id, same Developer ID team QAPB6CWYR6) was not testable from logs: the app's `FolderAccess`
  log lines are `<private>` in the unified log (`Engine refused folder access for <private>`, 3 times on 10-30: 09:19,
  12:37, 16:36, each at a spawn). Needs one run with the log made public for the path, or a bookmark-resolve test.

# The detector

## Intent

The UX has two things the engine lacks: a **measure** (a stall is timed, written to `stalls.log`, pinned by a
perf test with a ceiling) and a **place a person sees it** (the app says it is slow). The engine has the first half for
three things (warm-up failures, import stalls, held transactions) and nothing for the rest: a WARNING is a line, and
a line repeated 389,000 times is still just lines.

So: **count every WARNING-or-worse by what it says, turn a count that is too high into a named "degraded" state with a
reason a person can read, serve that state where the app already looks (`/api/health`), and fail the build when a
fixture or a real run produces a repeat nobody allowed.** The same loop the specs use: each silent class is a bullet,
each bullet names the test that proves the failure is surfaced and a log line that test reads, and a guard fails when
a bullet claims [OK] and the test is not there.

Design constraints (the owner's, and the other worker's):

* **Beside the log collapse, never inside it.** The log-collapse worker's branch (`feat/logs-stale-servers-support`)
  collapses per call site: `core/log_throttle.py::log_collapsed` writes the first 5 repeats of a template per minute,
  then one record whose `msg` is exactly `"%s — repeated %d times in the last minute"` with args `(template, held)`
  (`log_throttle.py:60-63`; `held` is the count beyond the 5). A ledger reading the *file* would undercount by 99 %; a
  ledger that is a `logging.Handler` sees the 5 and adds `held` from the summary record's args, so 5 + held is exact.
  The two features do not know each other, **except at one line**: both branches rewrite the `Database.embed` warning in `db/__init__.py` (theirs
  to `log_collapsed(..., cause=e)`, which takes no `extra`; ours adds `extra={"ledgered": True}`), see
  `engine.silent.ledger-counts-by-signature`.
* **Count the template, not the text.** Ids, paths and numbers make every line unique; the signature is the logger name
  plus the record's `msg` (the `%s` template, before its arguments); for an f-string message (no args) digits and hex are
  normalised to `N` (`failure_ledger.py`). Paths are not, which is the gap named in the same bullet.
* **Health is unauthenticated: a reason carries a class name and a count, never a path, id or message text** (the rule
  `startup_warnings.py:33-36` already keeps). The entry's own `id` is a 12-character hash of the signature, because the
  signature of a record the handler sees holds its message text; `test_a_degraded_id_carries_no_message_text`.
* **No new dependency, no thread, no I/O**: a dict under a re-entrant lock (a warning logged while counting must not deadlock), at most `MAX_SIGNATURES` = 500 signatures
  (`failure_ledger.py`); the clock is injected (`now=`) so tests need no sleep.

### C. The guard: no unallowed repeat reaches a release

- `engine.silent.scan-script` — **[OK]** (built 2026-10-30) `scripts/scan_engine_log.py LOGFILE [LOGFILE ...] [--ceiling N] [--allow REGEX ...] [--level WARNING|ERROR|CRITICAL]` is pure (stdlib, no network, streams the file line by line; a file with no newline is one line and is read whole), sums several files into one count (the engine's `engine.log` and a rotated `engine.log.1` are one log; pass both), reads lines in the engine's format (`asctime - name - level - message`, `LINE`; tracebacks, kraken's and `[PARALLEL]` prints are not log lines and are skipped), keeps WARNING and worse, normalises each to a template (uuid, hex of 8 or more digits with at least one digit, path, number → `<uuid>`/`<hex>`/`<path>`/`<n>`; a quoted path runs to its closing quote and an unquoted one to the end of the message, so spaces in it split nothing; the swallowed tail can merge two failures that share a prefix, a false FAIL, and an `--allow` on that shared prefix (or on `<path>`) then hides both: the limit is stated, not closed; a path runs to a closing quote followed by a space, punctuation or the end, so an apostrophe inside it is fine but a quote-then-space inside it leaks its tail; words before a path are printed; `_SUBS`), **adds the N of a "— repeated N times in the last minute" line to the written template its raw `%s` template stands for** (the raw template (`%%` read as `%`, each spec as "anything") must match a written template of the same logger whole; the most-written one when several match; **when unsure, fail**: with no match the summary is kept alone and checked against the ceiling together with the most-written line of its logger, and an `--allow` must cover every candidate and the summary's own raw template, so an allow naming only the cause does not hide it; `_fold`), and exits **1** when any template not matching an `--allow` regex is seen **more than** the ceiling (default 50), printing the offenders (count, level, first..last time, template). ## Open questions

1. **Where does the handler get installed?** Decided by the code: `core/logging.py` is not the engine's logging set-up (`configure_logging` is called nowhere; the handlers come from `logging.basicConfig` in `__main__.py:35`, which only the embedded app runs; the dev engine and the tests run uvicorn without it). So: the engine's `lifespan` in `api/main.py`, `logging.getLogger().addHandler(LedgerHandler())` once, guarded against a second install. It touches no file of the collapse worker's and covers every logger under every launch.
2. **Is "degraded" a health `status` value or a separate list?** Decided: a separate list. `status` is read as a word by `RemoteClientPairingFlow.swift:43` (`"healthy"`/`"ok"`), `LocalInferenceStore.swift:225` and the launch gate; a new value would make a working engine look down to them. The pill reads the list.
3. **Thresholds** (20 a minute, 200 total, 5 minutes quiet). The numbers are sound against the inventory: rows 1-3 (3,000 a minute) trip the rate in under a second, or the total within the first minute's summary under the collapse; row 15 (1,486 in a minute) and row 13 (26 a minute) trip the rate; row 12 (15 a minute) and row 6 (bursty, 12 a minute on average) trip the total within ~15 minutes; row 23 (491 over five days) is listed for 5 minutes after each hit once it passes 200, which is fair for a repeated refusal. Two caveats are gaps above, not threshold choices: the rate window must count the collapse's `held`, and the quiet period is wrong for a fault that only shows on use (an idle engine with a dead embedder is "fine" after 5 minutes). **For the owner:** confirm the recommended default in `engine.silent.ledger-success-clears` (an explicit-site entry stays until `ok()` or restart; quiet applies to handler-seen signatures only).
4. **Does the replace of the app trigger the originals loss, or any engine restart?** Not decided by the logs: every spawn filters the grants (`FolderAccessManager.swift:193,419`), so **any** restart drops a grant that covers no library, a replace included. Whether a replace *also* makes the stored bookmarks fail to resolve (then `restoreBookmarks` deletes them, `:513-517`) needs one launch after a replace with the path logged `privacy: .public`, or a unit test that resolves a bookmark minted by the previous build. Recommended default: build `originals-access-restored-after-update` for "any restart" (it covers the replace), and keep the resolve test as the owner's one run. **For the owner:** the one run.
5. **Two branches, one line.** This branch and `feat/logs-stale-servers-support` both rewrite the `Database.embed` warning in `db/__init__.py`. Whoever merges second resolves it as `log_collapsed(logger, logging.WARNING, "Failed to create embedding for %s: %s", doc.id, e, cause=e, extra={"ledgered": True})` after `log_collapsed` gains the passthrough, with `failure_ledger.note(...)` kept beneath it; `test_embedding_failure_degrades_health` must still see exactly one `search` entry.
