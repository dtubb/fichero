## Intent

Most of the world's digitised manuscripts, maps and archives are already published through
IIIF. A researcher should be able to work on them in Fichero **without first downloading the
collection**: paste a manifest or collection link, and the pages appear in the library at once,
drawn from the holding institution's image server at the size the screen needs. Transcription,
segmentation, models, notes and the knowledge graph then work on those pages exactly as on a
local scan. The pixels stay where the institution keeps them; what Fichero adds (segments,
readings, claims) is Fichero's.

In the other direction, everything Fichero knows about a source can leave as IIIF: a manifest
whose pages point back at the original image service, with Fichero's segments and readings as
W3C annotations on them, so Mirador, the Universal Viewer, Tify or another Fichero can show the
work. And a library that is shared can **be** a IIIF endpoint (images, manifests, annotations
and search), so colleagues can read it in any IIIF viewer, and a static export can publish it.

The same endpoint is how Fichero's own second screens get their pictures. An iPhone, an iPad or a
second Mac on a shared library asks the Mac for a page at the size of the pane showing it, and for
the visible region when zoomed, so a large scan never crosses the air whole. One way of asking for
pixels (a page, a region, a size) serves the Preview on the Mac, the devices, other viewers and the
published site.

## Prior art / best practices

- **IIIF Image API 3.0** (regions, sizes, `info.json`, compliance levels 0–2) and
  **Presentation API 3.0** (Collection, Manifest, Canvas, Range, AnnotationPage). Fichero adopts
  both, reads 2.1 as well (much of the world still publishes 2.1), and writes 3.0.
- **W3C Web Annotation** motivations (`commenting`, `tagging`, `linking`, `bookmarking`,
  `highlighting`, `assessing`) plus IIIF's own (`painting`, `supplementing`), and the **Text
  Granularity extension** (`page`, `block`, `paragraph`, `line`, `word`, `glyph`): the agreed way to
  publish transcription lines and words on a canvas. Transcription is `supplementing` with a
  granularity; a person's highlight stays `highlighting`, a note `commenting`, as the export does today.
- **Content Search API 2.0** (search inside a manifest, with hits as annotations) and
  **Content State API 1.0** (a link that opens a viewer on a region of a canvas).
- **Authorization Flow API 2.0** for access-controlled images, and **Change Discovery API 1.0**
  (an activity stream) so harvesters can follow a published library (not in this slice's behaviours;
  a later one, once there is a published library to follow).
- **By reference, not by mirror.** Arkindex stores a page as a pointer to a IIIF image server
  and fetches regions on demand; eScriptorium and Transkribus import a manifest by downloading
  every image. Fichero takes Arkindex's model, with an explicit, per-source choice to keep a
  local copy.
- **Servers in the field:** Cantaloupe and IIPImage (Image API), Omeka S's IIIF Server module,
  and static IIIF (level 0, pre-cut tiles) generated by tools like `iiif-tiler`. Fichero's
  static-site export (#3177) is level 0; a running shared library is level 2.
- **What viewers ask for.** OpenSeadragon, Mirador and the Universal Viewer read `info.json`, then
  ask for whole-image sizes from its `sizes` list and for tiles on its `tiles` grid at its scale
  factors. A client that keeps to those two lists gets answers a server (and the CDN in front of
  it) has already made. Fichero's own clients ask the same way, of the institutions and of the Mac.

## What exists today

Checked in the code and run 2026-11-21 (unit tests: 46 passed across
`tests/unit/importers/test_iiif_*.py`, `tests/unit/api/test_routes_iiif.py` and
`tests/unit/api/test_iiif_segments_as_annotations.py`).

- **Import by reference, as a job.** `POST /api/iiif/import` (`api/routes/ingest/iiif.py`,
  `import_from_iiif`) queues one `import-iiif` job in Activity (`importers/iiif_source.py`,
  `start`, `_run`). `import_source` reads the manifest or collection through the polite fetcher
  (`media/iiif_fetch.py`, `PoliteFetcher`: two requests per host, backoff, `Retry-After`),
  Presentation 2 or 3 (`importers/iiif_import.py`, `parse_iiif_url`), and writes one page row per
  canvas, 1,000 to an insert, into a folder that remembers its source (`metadata.iiif_source`).
  No image is fetched. Importing again adds only canvases whose id is not in the folder and counts
  the ones no longer listed. The app has File › Import from IIIF… and the folder's Inspector
  section with Refresh (`Views/Library/IIIFImport.swift`, `Models/IIIFImportStore.swift`).
- **What that import does not do.** A collection is flattened: every canvas of every manifest
  becomes a sibling page in ONE folder (`_remote_canvas_node` is given the collection as parent),
  so there is no document per manifest. Ranges (`structures`) are not read. The manifest's
  metadata is copied onto every page (`iiif_manifest_metadata`). Annotation pages on a remote
  canvas are not read (`annotation_jobs=[]`). No fetch is checked against
  `security/url_security.py` (`is_safe_url`); only the old loader does that.
- **Viewing.** The first time a page's thumbnail or display picture is asked for,
  `db/storage.py::iiif_page_image` fetches the whole image once at display size
  (`full/!2200,2200/0/default.jpg`) into `storage/iiif/`, and the thumbnail and display copies
  are made from it (`_resolve_thumbnail_cache_candidate`, `ensure_display`). `info.json` is never
  read, a canvas's `thumbnail` is never used, no region is ever asked for, and `storage/iiif/`
  is never evicted.
- **Steps.** A step on this Mac reading a by-reference page fetches it at 2,400 px on its longer
  side into `storage/iiif-steps/`, a cache that drops the least recently used past a share of free
  disk (`iiif_source.py::step_image`, `_evict`; called from `workflows/tools/sources.py::
  _resolve_abs_path`). A read package for a cluster lists Image API services, and the runner
  fetches them (`remote_read/package.py`, `remote_read/runner.py`).
- **The older, downloading paths.** `importers/iiif_import.py::import_iiif` reads a local folder
  of Presentation **3.0** manifests, collections and W3C AnnotationPages into documents, page
  text, entities and transcript results (#1646). `loaders/iiif_loader.py` fetches a remote
  manifest and **downloads** each canvas's image at up to 1,500 px.
- **Serving, dev tier only.** `api/routes/ingest/iiif.py` serves local images through Image API
  **2.1** (`/api/iiif/iiif/{id}/info.json`, `/{region}/{size}/{rotation}/{quality}.{format}`) and
  a Presentation **3.0** manifest per document (`/api/iiif/iiif/manifest/{document_id}`), with the
  working pass's lines (`/api/iiif/iiif/lines/{document_id}`) and the person's annotations as
  annotation pages. Its prefix is `dev` tier (`api/feature_tiers_generated.py`,
  `ROUTE_PREFIX_TIERS['/api/iiif']`), so no beta or release build has it, and that includes the
  import route the File menu calls. What it serves is measured below; much of it is wrong.
- **Export.** Parquet, IIIF, W3C annotation and RDF leave through one record stream
  (`export_service.py`); the georeference extension is read and written
  (`formats/iiif_georef.py`). The static-site export of manifests is designed, not built (#3177).

## The design

### A remote page is a page

A IIIF canvas brought in by reference becomes an ordinary page node whose image is a
**remote rendition**: the image service's base URI, its version and profile, and the canvas size.
Everything that draws or reads a page asks the storage layer for pixels at a size and region,
never for a file path (the standing "no local paths" rule). For a remote page the storage layer
requests exactly that region and size from the service and keeps it in a **bounded cache**.
Thumbnails, the Preview at any zoom, the Reader and the on-image segments all work this way.

Coordinates are always the **canvas's** coordinates, so a segment drawn on a remote page stays
put whatever resolution was fetched, and an exported annotation lands in the same place in any
viewer.

### A manifest is a folder; a collection is a folder of folders (2026-11-21)

- **A manifest** becomes a folder bound to the manifest's URL. Its canvases are its pages, in the
  manifest's order, each keeping its canvas id, label, size and Image API service.
- **A collection** becomes a folder bound to the collection's URL. Each manifest in it becomes a
  child folder bound to its own URL, and each nested collection a child folder of folders. A
  canvas is never a sibling of another manifest's canvases: two manuscripts that both have a
  "Front cover" stay two documents, each refreshed, read and exported by itself.
- **The collection appears at once.** Listing a collection costs one request (its members carry
  their id and label). The child folders are made from that list straight away, each marked "not
  read yet"; the job then reads the manifests one at a time, politely, and a folder the person
  opens is read first. A collection of a thousand manuscripts is browsable in seconds and
  complete in minutes, and a stopped job resumes at the first folder not yet read.
- **Ranges are structure.** A manifest's ranges (its table of contents: `structures`) become
  sub-folders when they divide the canvases cleanly (every canvas in at most one lowest range);
  the pages sit in their range, in order, and canvases outside every range stay at the top. When
  ranges overlap or a canvas sits in several, the pages stay flat and the ranges are kept on the
  folder as an outline the Inspector lists and the export writes back. Either way the ranges
  survive the round trip.
- **What is said once is stored once.** The manifest's label, summary, metadata pairs, date,
  rights, required statement, provider, homepage and "see also" links are kept on the manifest's
  folder. A page keeps only what is its own (canvas id, label, size, service, the canvas's own
  metadata) and reads the rest from its folder, as it reads its recipe (the cascade).
  The metadata pairs are kept verbatim, label and value, in the language the source gave; the
  ones that match a catalogue field (title, date, language, extent, shelfmark, creator) also fill
  it (`cataloguing.md`), so the Catalogue table and search see them.
- **Only public https addresses are fetched.** Every address a manifest names (a manifest, a
  collection, an image service, an annotation page) passes the same check as any other URL
  Fichero fetches (`security/url_security.py`): https, a public host, no credentials in the URL,
  and the check is made again on every redirect. A manifest cannot make the engine ask for
  something on this Mac or its network.

### What has to be fetched, and when

Three sizes of the same page, each fetched only when something asks:

- **Thumbnail.** What the Items grid and lists show. Fetched at thumbnail size when the cell
  scrolls into view: the canvas's own `thumbnail` when the manifest gives one, else
  `full/!512,512/0/default.jpg` from the service. Never the display size: a folder's grid costs
  kilobytes a page, not the megabyte a page it costs today.
- **Screen.** What the Preview and the Reader show at fit: the pane's size in pixels, rounded up
  to the next of a few standing sizes (1,024, 1,600, 2,200 px on the longer side) so two panes
  of nearly the same size share one fetch. The page before and the page after are fetched at the
  same size, quietly, while the person reads this one.
- **Detail.** What zooming in, a model run or "keep a local copy" needs: more pixels than the
  screen size holds. Zooming asks for the visible region only, on the service's own tile grid
  and scale factors (read once from its `info.json`), so the answers are ones the institution's
  server has already made. A step asks for the whole page at the size it reads.

A service has limits and Fichero keeps to them. Its `info.json` is read the first time a page
needs more than a thumbnail, and kept: the real size of the image, its `sizes`, its `tiles`, its
`maxWidth`/`maxHeight`/`maxArea`, and its level. A level 0 service is asked only for the sizes
and tiles it lists. Where a service answers a size request with a smaller picture than asked
(measured: a server that returns 1,200 px whatever larger size is requested), Fichero notices,
because it reads the size of what came back, and when a step needs more it asks for the page in
a few large regions and joins them. It never upscales and never pretends.

- **Keep a local copy** is a per-source choice (a collection, a manifest or a page): it fetches
  the full image once, stores it as a normal rendition, and from then on the page works offline.
  It is off by default and says how much it will download before it starts (from the sizes of a
  few sample images times the page count).
- **Offline.** A cached size is always shown, scaled if it is not the one asked for. A remote
  page with nothing cached shows a placeholder that says it is remote and cannot be reached now;
  it never shows a blank, and never says the file is missing. A host that did not answer is not
  asked again for a minute, so a grid of two hundred thumbnails makes one failed request, not six
  hundred. Importing or refreshing offline fails once, plainly, in Activity, and changes nothing.

### One cache, with a cap

Everything fetched from a remote service (thumbnails, screen sizes, regions, step images) lives
in one cache under the project's storage, keyed by the request that fetched it. Its cap is a
share of free disk with a floor (ruled 2026-10-04); past the cap the least recently used files
go first. Pages kept locally are not in the cache and are never evicted. What a source's server
says about freshness is honoured: a cached file younger than its `Cache-Control` age is never
asked for again, and an older one is revalidated with its `ETag` or `Last-Modified` rather than
downloaded again.

### Polite to the institution

The servers belong to the archives. One fetcher serves the whole engine (viewing, steps,
imports), so its limits hold across all of them:

- at most four requests in flight to one host, and of those at most two for background work
  (prefetch, a job walking a collection), so the page the person is looking at is never queued
  behind a crawl;
- `429` and `503` are obeyed: the `Retry-After` is waited out and the whole host slows down;
- failures back off, with jitter; a `4xx` other than `408` and `429` is not retried;
- the User-Agent says it is Fichero and where to read about it;
- nothing is fetched twice that the cache holds, and nothing is fetched in advance beyond the
  neighbouring pages.

### Running steps on remote pages

- **What is fetched.** Only the pages the step reads, at the size it reads them (2,400 px on the
  longer side unless the step asks otherwise), each once, into the cache. A step on a cluster or
  a GPU service fetches straight from the institution, never through the Mac
  (`../compute/hpc-runner-acenet.md`).
- **What stays remote.** The image. After the run the cached copy is ordinary cache: it may be
  evicted, and the page is still a reference. Nothing is copied into the library unless the
  person chose to keep a local copy.
- **What is the library's.** The segments (in canvas coordinates, scaled from the size that was
  read), the readings, the claims.
- **Provenance.** Every run on a remote page records what it saw: the Image API request (or the
  requests, when a page was joined from regions), the size that came back, the service's
  validator (`ETag` or `Last-Modified`) and a hash of the bytes. Two things follow. A result can
  always be traced to its pixels. And the standing rule that the same input and model are never
  run twice holds for remote pages: the input's identity is the canvas, the request and the
  validator, so a page whose cached copy was evicted and fetched again is not read again.

### IIIF folders: a folder that is a collection, in or out (2026-10-01)

Two kinds of special folder in the library, so IIIF is a place rather than a command:

- **A IIIF source folder** is bound to a collection or manifest URL (the British Library's
  Endangered Archives Programme, a university's digital library, another Fichero's published
  folder). Its contents are that collection, by reference. It **follows** the source: canvases the
  institution adds appear; ones it withdraws are shown as withdrawn (never silently deleted, since
  a person's segments and readings hang on them). Work done inside it (segments, readings, claims)
  is the library's own, as everywhere.
- **A IIIF published folder** is served as a IIIF collection (when the library is shared) and
  written as one in a static export: its documents as manifests, with their segments and
  readings as annotations. Moving or copying a document into it publishes it; out of it,
  unpublishes it. What the rights record withholds stays out.

A folder can be both: a source folder whose work is published back as annotations on the
institution's own canvases.

Like any folder, either can follow **its own recipe** (`source/models-chains-and-projects.md`,
the cascade): an EAP collection of Persian manuscripts in one folder runs a different reader from
the Spanish deeds next to it.

### Refreshing: what changed is said (2026-11-21)

Refresh reads the source again and says what it found, in Activity and on the folder:

- **Nothing changed** costs one conditional request per manifest and writes nothing. The folder
  keeps the manifest's validator and a hash of its content; a `304`, or the same hash, ends there.
- **Added** canvases appear, in the source's order. **Reordered** canvases follow the source.
  A canvas whose **label, size or image service changed** is updated in place and listed.
- **Withdrawn** canvases are kept and marked withdrawn, with the date; the Items pane shows the
  mark. If the source lists one again the mark is lifted.
- **A changed image.** When a cached image is revalidated and the source's validator or the
  bytes differ, the page says its image changed, and segments drawn on the old image are flagged
  for checking instead of silently sitting on new pixels.
- **Never two.** A canvas is matched by its id within its folder. Importing a URL that is
  already bound refreshes its folder; it never makes a second one.

### A million pages without slowing down (2026-10-01)

A IIIF collection by reference can be very large (a national library's digitised holdings run to
millions of canvases), and Fichero should take a million pages without the Mac slowing down.
That is possible because by reference a page costs almost nothing locally:

- **What the library stores is small.** Per canvas: its identity, its image service, its size,
  its label and its place in the tree; a few hundred bytes. A million canvases is a few hundred
  megabytes of rows, not terabytes of images. (Measured 2026-11-21: 3.4 KB a page today, because
  the manifest's metadata is copied onto each; `iiif.import.metadata-once` brings it back.)
  Importing walks the collection as a background job in the one queue (throttled, resumable,
  polite to the institution's server: it respects its rate limits and retries with backoff).
- **No thumbnails are made in advance.** A thumbnail is fetched from the image service, at
  thumbnail size, only when it scrolls into view, and kept in the bounded cache. The Library's
  lists and grids load lazily, so a folder of a million pages opens as fast as one of a hundred.
- **Heavy work runs where the compute is, and fetches from the source.** A recipe step on a
  million pages is sent to a cluster (ACENET), a GPU service or a Docker server. That machine
  fetches each image **directly from the institution's image service**, at the size the model
  needs, never through the Mac; it returns only the results (passes, readings, claims, and the
  pixels-seen provenance), which land as usual. The Mac only coordinates.
- **Search and the knowledge graph grow with the results,** indexed in batches as results land,
  not page by page.

### Honesty about a remote source

- **It can change or vanish.** See "Refreshing" above.
- **Rights travel with it.** The manifest's `rights`, `requiredStatement` and `provider` are
  stored on the source, shown in the Inspector, and carried into every export. A canvas behind
  IIIF authorization asks for access through the Authorization Flow; Fichero never stores the
  institution's credentials, and the access tokens the flow issues are kept for the session only, so
  no token is ever at rest in the library file.
- **The institution's text is a reading, not the truth.** Transcription annotations in a
  manifest (`supplementing`, with text granularity) arrive as a pass whose maker is the
  publishing institution, like any other imported result. Fichero's own corrections are new
  readings, never edits to theirs.

### Out

- **Export a manifest.** Any folder, document or selection exports as a Presentation 3.0
  manifest (or collection). A page that came in by reference points at the **original** image
  service, so nothing is re-hosted; a local page points at Fichero's own service (when shared)
  or at static tiles (in a static export).
- **What goes with it.** Segments become annotations with SVG or box selectors on the canvas,
  with text granularity (`block`, `line`, `word`, `glyph`). The counting reading of each segment
  is its text, with its language and maker. Other readings, notes, editorial facts and claims go
  as further annotation pages, each labelled, so a viewer can turn them on and off.
- **Round trip.** A manifest Fichero exported and then imports again lands where it came from:
  the same canvases, the same segments, no duplicate pages (the "test per path" rule: export,
  then import into a fresh library and into the one it came from). Three things make it hold.
  A by-reference page exports under the institution's canvas id, so import matches it. A local
  page exports under an absolute id that carries Fichero's own document id, so import into the
  library it came from lands on that document, and into a fresh library makes a by-reference page
  pointing at the exporting Fichero or the published site. And every exported annotation has a
  stable id made from its segment and reading, so importing the lines twice makes them once.

### Fichero as a IIIF server

A library answers IIIF requests through the engine's one port, with the accounts and permissions
it already has (`../transport/library-sharing.md`, #5049). There is no second server, no second
port and no toggle of its own.

**Version 1: pictures for Fichero's own screens, and manifests any viewer can read.**

- **Image API 3.0, level 2, for local pages**, answered from the **original** (or the edited
  page, where the page has edits), never from the display copy, so `info.json` gives the page's
  real size and that size never changes under a viewer. Regions by pixels and by percentage,
  `square`, sizes `max`, `w,`, `,h`, `w,h` and `!w,h`, rotation by 90s, `default`, `color` and
  `gray`, `jpg` and `png`. `info.json` lists `sizes` (the standing sizes above) and `tiles`
  (512 px, scale factors to the whole image). A request the server does not support is a `400`
  with a sentence, never a `500`. Answers carry an `ETag` and a `Cache-Control`. The 2.1 form of
  the same answers stays for old viewers.
- **Fast enough to feel instant on an iPad.** A size at or under a copy the Mac already keeps
  (the thumbnail, the display copy) is made from that copy, not from a 25 MB original. A tile is
  cut with a reduced decode where the format allows one, and kept in the same bounded cache. The
  budgets are in the behaviours.
- **Presentation API 3.0**: a document is a manifest, a folder is a manifest (its pages) or a
  collection (its folders), the library is a collection. Every `id` is an absolute URL that
  answers (#6806). A by-reference page's canvas keeps the institution's id and image service.
- **Fichero's own clients ask this way.** The iPhone, the iPad and a second Mac ask for a page
  at the pane's size (the standing size at or above it), the neighbours at the same size, and the
  visible tiles when zoomed in (#6572). The Mac's own Preview asks the same route for tiles when
  it is magnified past the display copy (#5031). One code path, local socket or network.
- **Remote pages, for the library's own people.** A by-reference page asked for by a signed-in
  account of the library is answered from the Mac's cache, fetched from the institution if need
  be: the iPad on the train sees what the Mac has seen. An anonymous viewer and every exported or
  published manifest get the institution's own service, never a copy (the ruling of 2026-10-04
  stands for the public; see Open question 6).
- **Access.** Only what the asking account may read is served. What the rights record or a
  permission withholds is absent from manifests and a `404` from the image service (the ruling of
  2026-09-28 that a deny hides, not marks). Requests carry the same token every other route
  takes.

**Later, on the same routes.**

- **Other people's viewers.** Mirador or the Universal Viewer in a browser cannot send Fichero's
  token; opening a shared library to them needs the Authorization Flow on Fichero's side, or a
  folder published openly. After version 1.
- **Annotations** for other readings, notes and claims as their own labelled pages.
- **Content Search API 2.0** inside a manifest, answered from Fichero's own search but returned in
  the API's own envelope: hits as annotations with text quote and position selectors, in an
  annotation page.
- **Content State** links: "Copy IIIF Link" on a selection gives a link that opens any viewer on
  that region of that page. The link is the API's Base64URL-encoded form, and the same form pasted
  into Fichero opens or imports what it points at.
- **Static publishing, level 0.** The static-site export (#3177) writes what the server would
  have answered, to files: for each page an `info.json` at level 0 naming exactly the `sizes` and
  `tiles` that were written, those files at the paths the Image API gives them
  (`{id}/full/{w},{h}/0/default.jpg`, `{id}/{x},{y},{w},{h}/{w},{h}/0/default.jpg`), and the same
  manifests and annotation pages with the site's address as their base. One builder makes
  `info.json`, the tile grid, the manifests and the annotation pages for both; the static writer
  only loops over what `info.json` promises. A by-reference page is not tiled: its manifest
  points at the institution. A library can then be published on any web host with no Fichero
  running, and what it publishes can be imported by another Fichero by reference.

### Trade-offs taken

- **Folders for manifests and ranges, not a flat list with labels.** It costs a deeper tree and a
  refresh that must move pages between sub-folders when ranges change. It buys documents that are
  the units a person reads, runs recipes on and exports, and no label collisions.
- **Thumbnails without `info.json`.** Asking `!512,512` blind saves a request per page (half the
  traffic of a grid) and works on every level 1 and 2 server measured; a level 0 server answers
  `4xx` and only then is its `info.json` read. The cost is one wasted request per level 0 page.
- **Standing sizes, not exact ones.** Rounding the pane up to 1,024, 1,600 or 2,200 px wastes up
  to a third of the bytes of an exact fit, and makes every resize of a pane a cache hit.
- **Regions joined on capped servers, not tiles.** Four to nine large regions rather than a
  hundred 256 px tiles: far fewer requests of the institution, at the cost of answers its CDN has
  probably not cached.
- **Pillow for version 1 of the server, not a tile server inside the app.** Everything the app
  needs ships inside it; Pillow is there already. Reduced decoding and the derivative copies meet
  the budgets on the measured scan; libvips or a pyramid file format waits until a measurement
  says they are needed.
- **The Mac answers for remote pages to its own people.** It spends the Mac's cache and the
  institution's bandwidth once instead of once per device, and lets a device with no route to the
  institution read. It is not re-publication: nobody outside the library's accounts is served.

### Acceptance (end to end, on a scratch library)

1. **Import a manifest.** Paste a public manifest of a few hundred canvases. Within two seconds
   a folder named for it holds a page per canvas; one request was made; the project grew by
   less than 1 KB a page; no image was fetched.
2. **Import a collection.** Paste a collection of several manifests. Its folders appear after
   one request; each fills as its manifest is read; no two manifests share a folder.
3. **Look.** Open the folder's grid: thumbnails arrive at thumbnail size, at most four requests
   in flight to the host. Open a page: it arrives at the pane's standing size; the next page is
   already there when turned to. Zoom in: only the visible region is fetched.
4. **Go offline.** Pages seen still show. A page never seen says it is remote and cannot be
   reached. Refresh fails once, plainly.
5. **Read.** Run segment and read on three pages: three images fetched at the step's size, the
   results in canvas coordinates, each pass naming the request it saw. Run again: nothing is
   fetched and nothing is read.
6. **Refresh.** Against a changed copy of the manifest (a fixture): one canvas added, one
   withdrawn, one relabelled; the job says so, the withdrawn page is marked and its segments
   are intact. Against the unchanged one: one request, no write.
7. **On the iPad.** Open the same library from an iPad: a page arrives at the pane's size, not
   2,200 px; zooming fetches tiles; a withheld document is not there.
8. **Round trip.** Export the folder as a manifest; import it into a fresh library and into
   this one: the same canvases, the same lines, nothing doubled.

## Rulings

- **2026-10-04 (#5323): the spec is approved by the maintainer with its four recommendations.**
  (1) The cache is a share of free disk with a floor, not a fixed cap. (2) A model run keeps the
  full image of a remote page while the source is in use, evicted with the cache. (3) Remote
  images are not proxied for viewers of a shared library; the manifest points at the original.
  (4) One storage call answers for local and remote pages (pixels for a page, a region and a
  size), and its shape is designed before `iiif.import.by-reference` is built. Status stays
  DRAFT: approved by the maintainer 2026-10-04; APPROVED status waits on a `Manual:` section (it
