## Intent

A scholar with two Macs works on one library from both. One Mac holds the library and runs its
engine; the other opens that library over the network and edits it, and each sees the other's
edits as they land. Turning it on is two switches and one pairing step, never a configuration
screen. Off the local network it works through Tailscale without exposing anything to the
internet. A second PERSON is a separate question (multi-user), answered by accounts, not devices.

## The rulings this rests on

- **Two toggles, independent** (ratified): *Sharing* (is the engine reachable from another device)
  and *Multi-user* (are there accounts for other people). Nothing else in Settings.
- **Accounts are for people, not devices.** Local use logs in as owner; a remote device always
  authenticates. Roles: owner, editor, viewer. Libraries are private by default and shared
  explicitly.
- **Transport:** HTTPS always, with a self-signed certificate pinned by its public key (SPKI) on
  the client. The host reaches its own engine on loopback. Off-network reach is `tailscale serve`
  (never `funnel`); Tailscale is connectivity, not identity.
- **Loopback with the bootstrap token is always owner.**
- **Pairing:** the host shows a QR / one-time code; the device sends it to `POST /api/pair` over the
  pinned connection and receives its own token, revocable per device.
- **2026-10-17:** shared editing (a deletion on one Mac is a deletion on the other); no open lookup of libraries; Multi-user sits beside Sharing; `.ts.net` is system trust, `.local` is the SPKI pin; the owner account owns every library.
- **2026-10-18 (later, SUPERSEDES the next line): multi-user is always on, no switch, no ambient owner** — see `multiuser-always-on.md`.

- `sharing.synced-project-names-its-host` — **[PARTIAL]** (**#5898**, ## 539/542/544; engine writer built, unrun; the guest engine reads and validates it, r1, `security/synced_host.py`) THE FILE CONTRACT (one text): a project that is shared with a person carries, in its project root (the `.fichero` package directory itself) beside the library, a small NON-SECRET file `sharing-host.json` with exactly FOUR keys: `{"hostURL": "https://<host>:<port>", "hostName": "<the name the person sees for this Mac>", "person": "<the host's person>", "hostEngineId": "<the host engine's stable id>"}`. `hostURL` is an `https` ORIGIN only (scheme, host, port: no path, query, user or password), the same address the pairing link carries; with no `https` public address there is no file. `hostName` is the Mac's name as System Settings shows it (`scutil --get ComputerName`, else the host-name label), CLIPPED to what the guest's reader accepts (control characters dropped, nothing link-like, 1-200 characters; `person` is clipped the same way). `person` is the HOST's person, the one the guest is told to ask ("Ask Daniel for a pairing link"): the person who shared (else the owner), NEVER the person an invite is for (a project is shared with 2-10 people, and an invitee's name must not travel in a file). `hostEngineId` is the engine id the sign-in challenge already reports as `engine_id` (`accounts._engine_id`), not a secret. The file carries NEVER a token, code, pin, secret or account id.
  *Who owns it, and how that is known (## 542/544):* ownership is by ENGINE ID, never address: the FIRST engine to share a project records itself (it writes the file when none exists), and from then on only that engine rewrites it (`synced_host.is_this_engine(hostEngineId)`). The first engine to share owns the file from then on. If two engines DO both write it before a sync has delivered the other's (two Macs sharing the same project at once), the sync service keeps one under the exact name `sharing-host.json` and sets the other aside as its own conflict copy (a renamed file, for example "sharing-host 2.json"): the reader reads only the exact name, so the conflict copy is ignored and harmless, the file that kept the name decides the owner, the other engine now finds another engine's id in it and never rewrites it, and the owner can delete the stray copy. A guest's own engine, which holds the synced copy and may have Sharing on, never writes its own address over the host's; a file that names another engine, or that this engine cannot read as its own (corrupt, three keys from before engine ids, extra keys), is LEFT as it is, and deleting it is the owner's call. The guest's own check uses the same helper.
  *Who writes it, and when (built):* the HOST engine, in the share action (`POST /api/authz/share`, `_name_the_host_in_the_project`), after the role is granted: whenever a library is shared with a person it writes the file into the library root (`fichero_server/sharing_host_file.py`), if it owns the project. It writes to a UNIQUELY named temp file in that directory (so two Macs syncing the folder cannot collide on one temp name) and replaces atomically, so a sync client never sees half a file, and it writes only when the text would change, so a second share leaves the file byte-identical. A failure (no `https` address, an unwritable directory) is logged and never raised: the share still succeeds and the guest just has no host to ask. The app is not involved; a guest cannot write it.
  *Guest side (built, Swift part unbuilt; r1):* the GUEST engine reads `<package path>/sharing-host.json` (`security/synced_host.py`), validates it (exactly the FOUR string keys; `hostURL` an https origin only; names 1-200 chars and not link-like; 2 KB cap; anything else is logged and ignored) and reports it as `synced_host` on `GET /api/registry/open`, one per open project; the app reads only that field and never the project root. The engine OMITS `synced_host` when the file names THIS engine (identity by ENGINE ID, never address: `is_this_engine(hostEngineId)` / `host_to_ask()`; Sharing off or a changed address still asks nobody), so the host's own copy asks nobody.
  *What it costs:* the file travels wherever the project is synced, so whoever can read the synced folder learns the host's name, address and engine id; the address is the same fact the pairing link carries, the engine id is already reported by the sign-in challenge, and none of it grants anything (a connection still needs the one-time link, `sharing.synced-device-pairs-by-host-code`). *Not built:* removing the file when sharing is turned off or the last person is unshared (the file then names a host that no longer lets anyone in, which the guest's ask handles by failing in words), and leaving it out of a published export (an export lists its files; the file is not part of any).
  *Tests:* `fichero-server/tests/unit/security/test_sharing_host_file_5898.py` (unrun): exactly four keys and no secret, and the guest's own validator accepts what is written; an `https` origin only; a rewrite with nothing changed leaves the file alone; the owning engine rewrites on a change; a GUEST engine never overwrites another engine's file; a file this engine cannot read as its own is left alone; the first engine to share records itself; no `https` address writes nothing; the temp name is unique and none is left; an unwritable root logs and does not raise; the host name is the name the person sees; a long, link-like or control-character name is clipped so the guest's validator still accepts the file; the share helper names the sharer. Guest side: `fichero-server/tests/unit/security/test_synced_host_file_5898.py`.
- `sharing.person-bound-invite` — **[PROPOSED]** (**#2403** slice 10 brought forward; **#5902** case 2, release-blocking: a shared server on the owner's tailnet used by 2-10 people, each with their own account and library access; **#5898**; owner via manager 2026-10-20; SPEC ONLY, no code, and the engine change needs the manager/owner OK before any is written; it adds routes and response fields, so an OpenAPI regen follows, HELD) the owner can give a NEW person access to ONE project in a single step that cannot make a device the owner by mistake. This is the engine half `sharing.synced-device-pairs-by-host-code` marks `[GAP, engine]`.
  *Who it is for (ruled 2026-10-20):* a person who has NO account yet. The route makes a NEW account only and REFUSES an existing username, in words ("Maya already has an account: share the project with her instead"). A person who already has an account gets a library through the existing share (`POST /api/authz/share`, a role grant) and pairs their own Mac as themselves (`sharing.device-chooses-person`); no invite link ever binds a device to an account that already exists, because a device is bound to an ACCOUNT, not a library (`_authenticate_device` reads `device.user_id`), so it would act as that person in every library where they hold a role.
  *Flow:* in the share sheet the owner NAMES the new person (and picks a role). In that one step the engine (1) makes the account, (2) grants the role on that ONE library, (3) writes the invite row (below) and (4) the sheet shows the pairing LINK (the guest takes the link only: `sharing.synced-device-pairs-by-host-code`; trust comes from the link, #5891: `.local` pinned, `.ts.net` system TLS, plain http refused). The person opens the link on their Mac; the device that redeems it is bound to THEM and acts only as them (`sharing.device-acts-as-its-binding`, S1).
  *Refused at MINT, not only at redeem:* a role of `owner` (`VALID_ROLES` allows it; an invite does not), and any name that is an owner or admin account, including the owner's own (`is_owner`), so no invite can ever produce an owner device. The refusal says which of the two it is.
  *The invite row (app DB, not memory):* a person-bound invite lives for hours or days and must survive an engine restart and be listed and revoked, so it is a row in the app database, NOT the in-memory `_PAIRING_CODES` dict (that stays for the 10-minute own-Mac pairing code only, `PAIRING_CODE_TTL`). The row holds a HASH of the code, never the code (a database read must not leak a live bearer; the code is shown once, in the link), the invited account, the one library, the role, who made it, created and expiry times, and a state: `pending` -> `used` | `revoked` | `expired`. Every change of state is ONE compare-and-set (`UPDATE … SET state = <new> WHERE id = ? AND state = 'pending'`, and only the caller whose update changed a row proceeds), so a redeem and a revoke cannot both win: whichever commits first decides, the other gets nothing and does nothing. Redeem pairs the device only after it wins `pending -> used`; revoke removes the made account only after it wins `pending -> revoked`. The compare-and-set, the account's activation and the device row are ONE database transaction (all three or none), so a crash between them leaves a pending invite, never a used invite with no device or an active account with no invite. The redeem request carries only the code and the device name; `username`/`password` on `POST /api/pair` are IGNORED for an invite code, and the role is fixed when the invite is made, never read from the redeem. Access to any OTHER library is separate: the account has a role only where the owner granted one (`library_roles`), so scoping to one project is the grant, not the token.
  *The made account cannot sign in until the invite is redeemed:* it is created with NO password (or an unusable hash) and inactive for every sign-in path: the username/password login, a session, and the redeem's `username` path. A pending invite therefore leaves a guessable username with no credential behind it. It becomes active only when the redeem wins `pending -> used`, in the same step as the device it pairs. (The account then has no password and only that Mac's device token, so a lost Mac is a revoke, not a password reset; whether the person may set a password is the owner's open question 3.)
  *Expiry, list, revoke (all ship WITH the route that issues the invite, never after):* an invite expires (a longer life than the own-Mac code's 10 minutes is proposed, because the link is sent by message: open question 2). Expiry is swept ON READ ONLY (every list and every redeem checks `expires_at` and moves `pending -> expired` by the same compare-and-set), with no timer and no background sweep: an expired invite nobody reads stays `pending` in its row until the next list or redeem, and its made account stays (inactive, no credential) until then. That costs nothing, because every path that could use the invite goes through the sweep first. The owner lists invites in Settings > Sharing > People: pending (person, role, expires), used (which device, when), expired, revoked. One guard removes the made account whenever an invite ends unused (revoked OR expired): the account is removed only if this invite made it, it is still unredeemed, and it has no other grant and no device. Revoke after use removes the person's role on that library and revokes the devices that invite made (the existing device revoke), so their Mac stops being let in; it says so in words ("Maya's Mac can no longer connect"). An invite never leaves an account behind.
  *Threat notes (what someone holding the link can and cannot do):*
  - CAN, once, before it expires or is revoked: redeem it and become THAT new person with THAT role on THAT library. The link is a bearer: an attacker who reads it before the person does gets their access. Mitigations built into the shape: one use (one compare-and-set, so two simultaneous redeems yield one device and one refusal), a limited life, the list shows "used by <device> at <time>" so the owner sees an unexpected use, and revoke after use takes it away. The owner sends the link by a channel they trust.
  - CANNOT: pick another person or the owner (the redeem names neither, and the account was new); raise the role (fixed at mint, `owner` refused); reach another library (no grant there, and the account is new); act as the owner by fallback (S1: an owner session needs the Keychain key, a paired device never has it); replay it; outlive expiry or revoke (the state is checked and changed in one step); learn anything from the link beyond the host's address and the pin the link already carries (the invited person's name is not in the link).
  - One answer to a caller: a used, expired, revoked and unknown code all answer the same 401 as today ("invalid or expired pairing code"), so a guesser learns nothing. Only the OWNER'S list says which ("already used", "revoked", "expired").
  - Brute force: a code is 8 characters from 32 symbols (about 40 bits) and `POST /api/pair` allows 5 tries a minute per rate-limit scope (`PAIRING_RATE_LIMIT`, `PAIRING_RATE_WINDOW`); that is far out of reach for a guesser even over a week. The scope (`_rate_limit_scope_from_request`) is the device, session or user when there is one, else, behind `tailscale serve` where every caller arrives from loopback, the proxy's Tailscale identity header (trusted only on loopback, #5320, #5350), so each person on the tailnet has their own bucket and one person cannot lock pairing out for the others; a caller with no identity at all on loopback shares one bucket. A link is pasted, not typed, so a longer code for a multi-day invite is a free choice (open question 4).
  - The owner is never minted: no code, token or session this flow makes is the owner's, and no step reads the host's signed-in person as the invitee. The own-Mac link (`create_pairing_code`, which binds to whoever mints it and so pairs the owner's OWN Mac as the owner) stays on the Settings card for the owner's own devices only.
  - Audit (`one-audited-action-layer`): mint, revoke and the removal of the made account or role are the OWNER's actions (the owner is the actor); the REDEEM is the new device's own action (its actor is the invited account and the device, with the invite's id), so Activity can say who invited whom and who accepted.
  *OPEN QUESTIONS for the owner:* (1) the DEFAULT role when he names a person: `editor` (can read, correct and add) or `viewer` (read only); the sheet always shows the role and lets him change it, but the default is his to set. (2) The invite's life: a day, a week? (3) Does the invited person set a password on first use, or has the account none and only that Mac's device token? (Recommended: none; a lost Mac is a revoke.) (4) A longer code (for example 12 characters) for multi-day invites?
  *Tests to write once approved (engine, red first; #5902 asks for a test per case with FAKE devices: case 1, one person's Macs and iPhones tied to one account, and case 2, 2-10 people on one tailnet server, each with their own account and only the libraries they were given; a live check with two real people on the tailnet comes before release):* an invite for an existing username is refused; an invite for the owner or an admin account, or for the role `owner`, is refused at mint; the made, unredeemed account cannot sign in by password, session or the redeem's `username` path; an invite redeemed once pairs a device bound to the invited account with exactly the granted role on that one library; a second redeem, an expired invite and a revoked invite all answer the same 401; `username`/`password` on the redeem are ignored; a redeem and a revoke raced against each other produce exactly one winner, a device bound to a live account or a removed account with no device, never a device bound to a deleted account; the row holds a hash and the list never returns the code; expiry on read moves `pending -> expired` and removes the made account only by the one guard; revoke after use removes the role and the device; a non-owner cannot mint, list or revoke; the redeemed device cannot read another library (`test_device_acts_as_its_binding`-style); two people behind one `tailscale serve` do not share a rate-limit bucket. App (Swift, needs compile): the sheet names the person and role, shows the link, and lists pending and used invites.

## The two-machine test (next)

On the Air (host) and the MBP (client), apps launched by path, one xcodebuild at a time on each:
1. Air: Sharing on; read the advertised address, the listeners (`lsof -iTCP -sTCP:LISTEN`), the
   Bonjour record (`dns-sd -B _fichero._tcp`, `dns-sd -L`).
2. MBP: paste the invite link; pair; open the shared library.
3. Edit on the MBP (rename, a reading); see it on the Air. Edit on the Air; see it on the MBP.
4. Revoke the MBP on the Air; the MBP is refused.
5. The same over Tailscale (`tailscale serve`), by hand, to learn what automating it needs.
Each failure: an issue, fixed one at a time, its behaviour above re-tagged.
